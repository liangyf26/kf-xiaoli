## 必须修

**N1 封存题：改题面、改 `questions.sha256`、保留每行 `sha256` 字段，三处这样组合能通过。**
- `heldout.py:95` 的 `key = _set_key([it["sha256"] for it in items])` 取的是 jsonl 里存的字段，不是按题面现算的。
- `:88-93` 只拿题面和 `questions.sha256` 对照。所以只改题面加 sha 文件、不动每行字段，set_key 不变，账本照常放行。
- 实测：`tamper-text+shafile-keep-field ACCEPT 10`。
- 修法：key 由 `_sha(it["question"])` 现算，并断言每行 `sha256` 字段和现算值一致。

**N2 预取：最后一批正在生成时，pose() 提前返回 None，后面的题全部丢失。**
- `run_round.py:605` 判 `seen >= n` 就返回 None。但 worker 在 `_try_reserve` 里已经把 seen 推到 n，`busy=True`，planned 还没追加，这时消费端会误判「弹尽」。
- 如果这一批随后失败，seen 回退到 20，这一段题就彻底丢了。
- 实测 40 轮压测（随机延迟，一半注入 15% 失败），5 轮出 None：
  - run0：n=60，在第 50–59 题；run9 同。
  - run3：n=30，在第 20–29 题，失败回退后 seen=20、planned=20。
  - run18、run26：n=30，在第 20 题之后。
- 非 None 的题全部按 spec 顺序，没有重复。
- 探针 4 的时间线（n=20，两批都由 worker 出，fallback 一次等了 164s）没有触发，因为消费比出题慢。答题一快就会撞上。
- 修法：`seen >= n` 改成 `seen >= n and not busy and next >= len(planned)`；busy 时等待交货。

**N3 预取：蓝方持续失败时，pose() 无退避地热循环，整轮永不返回。**
- `:607-610`：池空且不 busy 就调 `_fill_guarded()`，失败返回 False 后立刻重来，没有 sleep，也没有次数上限。
- 实测：3 秒内调用 ask **204,208 次**，`errors` 记了 204,207 条，pose 线程 3 秒后仍然存活。
- 对真端点就是每秒约 7 万次请求的压测，`blue_fill_errors.jsonl` 也会被刷爆。旧版 `_fill()` 失败会抛错，现在反而更糟。
- 修法：主循环自补失败要退避，连续 K 次失败就抛错或返回明确的失败状态，让局按「失败只记录」收尾。

**N4 并发测试和调度仍然靠 sleep 轮询（Chief 要求改成事件驱动）。**
- 测试：`test_round.py` 里还有 25 处 `time.sleep` / `deadline`，例如 `while time.time() < deadline and st["seen"] < 30: time.sleep(0.05)`。
- 调度本身：`run_round.py:577` sleep 1.0，`:583` sleep 2.0，`:613` sleep 0.2。
- 这次 8 连跑都是 28 passed（0.63–3.75s），但时长波动 6 倍，靠的是时间余量。
- 修法：用 `threading.Condition`，在 fill_end、pop 和失败时 `notify_all`；worker 和 pose 改用 `wait(timeout)`；测试用 Event 等「worker_exit / seen==n」，不再轮询。

## 建议（不阻塞）

- **S1**：`sample(9,60)[:10] != sample(9,10)`（另测了 60/30、30/10、45/20，均 False）。同 seed 只有在 n 相同时才可复现。max_questions 一改，前 10 题就全变了。要么在任务书里写明「可复现以 (seed, n) 为键」，要么改成前缀稳定的抽样。
- **S2**：worker 线程不会被叫停。一局消费 5 题就放弃，线程永远挂着：建 3 次后还剩 3 个 `blue-prefetch` 存活。同进程多轮跑会堆积。建议加 stop event，在 run() 的 finally 里置位。
- **S3**：conftest 只守 `data/`，没守 `runs/`（`used.jsonl` 在 runs/ 下，a052fde 修过一次泄漏）。建议把 `runs/adversarial/heldout/used.jsonl` 也纳入快照。
- **S4**：`_check_unused` 和 `_claim` 之间没有文件锁，两个进程同时跑同一套题可能都放行。目前是单命令串行，风险低。
- **S5（范围外）**：全量 pytest 里 `tests/test_phase3_units.py` 等用例会直连 `172.28.29.24:30032`，被网络守卫拦下 5 次，`test_llm_client_timeout_message` 因此失败。所以「全量 pytest」本身会去压红方端点，和「采样期间不碰 30032」冲突。建议给这类用例加真端点 skipif 或 marker。
