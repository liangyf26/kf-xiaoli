### 2.1 两种模式（共用 `classify.py` / `judge.py` / `match_log.py` / reset / 修库流水线）

群聊模式流程（用户提）：蓝队 Bot 在群里出题并 @红队 → 红队 Bot 调 `ask_kf.py` 把题转给 kf 隔离实例 → 脚本原样输出回答，红队贴回群，同时逐题落盘。

防跑偏硬规则：
- 题面不经 Bot 转述：蓝队调 `blue_pose.py` 落盘题面与出题理由，拿到题号；红队只把**题号**传给 `ask_kf.py`，脚本按题号从日志取原文发给 kf
- 推进权归脚本：追问次数、4 个终止条件、计分、比分、下一步由 `ask_kf.py` 读状态文件 `game_<k>/state.json` 判定，输出末行固定为 `NEXT: blue_followup <话题> | blue_new | game_over`，Bot 照做，不能自己宣布得分
- 裁判只读落盘日志；群里文字被改写不影响计分（Reviewer 实操 ④）
- 卡住兜底：`state.json` 记最后动作时间，超过 `stall_s: 600` 无动作，下一次调用把该题记无效样本；连续 3 题卡住整局标作废

| | 程序模式 | 群聊模式 |
|---|---|---|
| 谁驱动 | `run_round.py` 一条命令 | 蓝队/红队 Bot 轮流调脚本 |
| 无人值守 | 是 | 依赖 Bot 按 `NEXT` 行动，需兜底 |
| 每题耗时（估算，阶段 3 实测替换） | kf 作答 + 蓝方出题，约 0.5~2 分钟 | 再加两次 Bot 轮次，约 2~5 分钟 |
| 100 分长局（≤300 题） | 约 3~10 小时，可批量 | 约 10~25 小时，不现实 |
| 上下文 | 无累积 | 每题约 2~4k token 进两方会话，60~100 题撑满 235k；需每局换会话或压缩 |
| 直播 | outbox 摘要转发 | 过程天然在群里 |
| 适合 | 20/50/100 分正式局、批量 | 10 题演示局、复盘回放 |

推荐：**正式局默认程序模式**，过程按 `level` 摘要推群；**群聊模式只用于 ≤20 题小局**，每局一个新会话。阶段 2 先做程序模式，`ask_kf.py`/`blue_pose.py` 复用同一套函数，放在阶段 3 试跑后再接（工作量约 0.5 天）。

### 阶段 2：对局编排 + 归类裁判 + 日志 + 直播（Coder，约 1 天）

交付文件（新建，均在 `tests/adversarial/`）：

| 文件 | 职责 |
|---|---|
| `run_round.py` | 总入口：读配置 → 起隔离实例 → 跑 N 局 → 修库流水线 → 轮末汇总 → 推日志 |
| `match.py` | 单局编排：蓝方出题 → 红方（隔离实例 WS 路径，复用 `ab_run.py`）作答 → 裁判 → 追问 |
| `classify.py` | 题目归类裁判 |
| `match_log.py` | 落盘与对账 |
| `broadcast.py` | 写直播 outbox（转发到 DS Bot 群） |
| `ask_kf.py` | 群聊模式：按题号把题面原样转 kf 隔离实例，落盘、判分、打印固定格式结果 |
| `round.yaml` | 默认配置 |

**单局规则**（与 PRD §2.3 一致）：
- 一来一回；同一话题追问≤3 轮；话题终止取 PRD :187 四条：①红方已失分 ②已判出结果 ③追问满 3 轮 ④蓝队主动换题
- `mode: fixed` 跑满 `questions` 题（试跑用）；`mode: race` 先到 `target_score` 停，上限 `max_questions`
- 单题超时 120s；超时/断连/5xx 按 `retry` 重试，仍失败记无效样本（双方 0 分、计入分母）；无效 >10% 整局标作废，继续下一局
- 蓝方出题复用风格池 `style_sampler.py`（去掉「红方交空答案」，接入真实红方答案）

**归类裁判 `classify.py`**（自动，无人）：
1. 范围判定：先查蓝队给定范围/品类清单（规则），清单未覆盖再问蓝方模型并要求给出依据，依据落盘
2. 有库/无库：用生产检索入口查库，top3 命中且 `judge.facts_ok` 关键词可对上 → 范围内有库；否则 → 范围内无库（蓝 +1，记知识缺口）
3. 计分：有库题走 `judge.py` 硬断言；**开放题只记录不计分**，直到一次性校准通过（阶段 5）
4. 每题落盘归类结论、规则命中项、模型依据原文

**日志（参照技能 baseline-reproducibility）**，目录 `runs/adversarial/<round_id>/`：
- `meta.json`：git commit、配置全文（密钥脱敏）、双方端点/模型/温度/seed、库副本 sha256、风格卡版本
- `game_<k>/turns.jsonl`：逐轮一行（题面、风格、蓝方选题理由、红方答案、sources、path、耗时、重试次数、归类与依据、判分、终止原因）
- `game_<k>/kb_changes.jsonl`：本局登记的缺口与修库建议（不当局生效）
- `summary.json`：分母对账（期望题数=结果数=有效+无效），不对账则 exit 3
- 复算：`python -m tests.adversarial.match_log --recompute runs/adversarial/<round_id>` 只读 jsonl 重算分数，与 `summary.json` 一致

**直播 `broadcast.py`（目标群：DS Bot 群「kf红蓝对抗直播」，用户 10-27 定，不用飞书）**：
- DSH 查证结论（ds-bot 0.2.2，`node_modules/ds-bot/src/host/channel.js`）：唯一外部入口是 Web 的 `POST /api/bot`，其 `send` 分支 :404-421 把文本当**用户消息**排进会话（`mode: 'queue'`），每条都会触发群内一轮 Bot 回复，不是「静默写一行」；鉴权方式未查实（待考）。**结论：没有适合脚本逐条写群的接口，不用 `send`。**
- 采用中间文件 + 转发：
  1. 脚本只写 `runs/adversarial/<round_id>/outbox.jsonl`（一行一批，字段 `seq, game, kind, text, sha256`）；`kind` ∈ 开局参数 / 出题+出题理由 / 回答 / 追问 / 判分 / 比分 / 小结
  2. 转发者用 DS Bot 定时任务（`every_seconds: 60`）读 outbox 新增行，原样 `post_to_group`，末尾带 `seq` 与 sha256 前 8 位；已发 `seq` 记 `outbox.sent`
  3. 转发者=**红队 Bot**（用户 10-27 定）。红队是非 admin，不带 @ 的帖子只写入、不触发轮次；转发时只原样贴 outbox 文本，不加评论
- 延迟与代价：延迟 ≤60s + 转发一轮耗时；每批一次模型调用（约 1~3k token），10 题小局约 10~20 批；长局按小结粒度播，否则成本随题数线性涨
- `level`：`all` 全过程 / `lost_only` 只播丢分题 / `summary` 只播开局与每局小结 / `off`；当前 `all`（用户 10-27 定，10 题试跑全播，消息太多再改）
- 限速：脚本写 outbox 时按令牌桶 ≤2 条/秒，超出合并成一批；转发端每分钟一批天然合并
- 失败不阻塞：写 outbox 失败只记 `broadcast_errors.jsonl`；转发失败不回写 `outbox.sent`，下次重试，不影响对局
- 每局小结：比分、无效样本率、平均耗时、能判题占比、丢分题前 3、GitHub 日志链接（`adversarial-logs` 分支）
- 局后败局分析：小结批末尾带 `@红队 @蓝队`，红队讲败局与修库建议（写 `kb_proposals.jsonl`），蓝队讲下一局打法；**不阻塞下一局**，建议在下一局开始前进门禁，赶不上就顺延一局
- 群里文字只供观看，**裁判与计分只读落盘日志**；内容不放密钥和内部库原文（D4 口径）

### 阶段 5：held-out 复测 + 开放题一次性校准
